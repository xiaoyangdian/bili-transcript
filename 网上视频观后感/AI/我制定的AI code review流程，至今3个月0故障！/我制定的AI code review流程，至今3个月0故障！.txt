AI 生成的代码，大家还 review 吗？这期我就想来跟大家分享一下，我的团队是怎么去做 AI 生成代码的 code review 的。

可能大家会好奇，我前一阵子不说我已经不 review AI 生成的代码了吗？现在绝大部分情况，我确实不会亲自让人去 review 了，因为 AI 生成的代码太快了，产量也太高了，如果让人去 review，反而会成为整个研发流程的瓶颈。但是就像我说的，只是绝大部分情况下我不让人去 review 了，但是我还是要 review，让谁去 review？让 AI 去帮我 review。

另外还有一种极端情况，还是要人去做兜底的 review 的。具体什么极端情况，你看完这个视频你就知道。

让 AI 去 review AI 生成的代码——如果 AI 能 review 出来自己的代码有问题，那为什么最开始就写出这种不需要 review 的代码呢？好问题。就是我们 review 的这个 AI agent，它跟写代码的这个 agent，它的上下文跟提示词都是不一样的，会起新的 agent 去 review 代码，而不是让写代码的这个 agent 来 review，这样才能避免我前面说的这种问题。

当我们在 review 的时候，其实我定了三个标准跟维度的：

第一个点就是需求的正确性，看一下它是不是能够完整地满足我们提的这个用户需求。

那第二层 review 就是看它的实现是不是跟这个需求是保持一致的，这个功能的输入跟输出是不是正常的。

第三层 review 就是系统层面的 review，有没有把原先的老逻辑给改坏，或者存在一些并发问题、分布式事务的问题。

所以对应这三个层次，简单的需求一个 agent 就能够去完整地覆盖这三个层次的 review；那如果是比较重要、比较复杂的变更，我们就会起三个 agent 分别去 review 这三个层次的问题。

在 review 的过程当中，AI 可能会提出一些问题，但是在我们看来其实并不是什么缺陷，那我们也会把这些规则添加到这些白名单里面去，后面再遇到类似的问题可能就直接跳过了。迭代过几次之后，我们这个 review agent 就越来越顺手了，review 出来的这些问题都是我们实际需要去关注的问题。

那第二个点就是我们 review 的这个时机。首先 AI 根据需求写完代码之后，我们会进行初步的 review；另外就是在发布之前，跟其他分支已经合并了之后，再去跑一次这个完整的 review。

为什么要跑两次呢？第一次是保证每个独立的需求，它的这个分支是没有什么问题的；第二次是保证多个分支、多个需求合并之后，这个分支也是没有问题的。因为之前我们确实踩过一个坑，就是每一个单独的分支都是没问题的，但是合并在一起就会出现各种问题，第二次 review 就是为了去避免这种问题。

那为什么不直接保留第二次发布之前的这个 review 就行了呢？因为如果流程推进到这个时候，再去发现里面的一些风险，那这个改动成本就是比较高的。并且这个时候如果出现了一些比较大的问题，如果是设计上的问题，那这个时候要把这个独立的分支从合并的分支里面再踢出来，这是一件比较麻烦的事情。

总之我们的一个原则就是尽量在早期去暴露这个风险。所以这两次 review 都是有意义的，值得去做的。

那第三个点就是什么情况下我们还会去人 review 呢？我们现在每次需求的变更都会去做一个定级，看这一次变更它的这个风险程度有多大。如果这个风险比较高，涉及到核心链路，我们还是会去安排人去做一层 review。

软件的实现层面我们尽量地让 AI 去做，把人的职责重新收敛到需求分析、产品业务的取舍、流程规则定义跟接口的约束。这些东西主要就是人跟人之间的交流，还有就是人跟 AI 之间的交流，尽量避免人去直接接触这个执行层面的事情。

这就是我给我们团队现在定义的这个 review 的流程。我在几个月前就引入了这套方式，至少这几个月我们线上是没有什么故障。大家可以参考我的这种方式，但是并不是完全的照抄，这并不是一个标准答案，大家也可以结合自己的团队跟产品的复杂性，结合自身去做这个代码质量的保证。

今天我们就给大家分享一下我们团队现在用的这个流程。如果大家认为讲得还不错，也希望多多点赞、转发，没关注的同学别忘了点关注啊，你后面就不会错过这一期说干货了。
