# 对咨询者的答复与我的想法

> 日期：2026-10-31
> 来源：同主题视频《我制定的 AI code review 流程，至今 3 个月 0 故障！》的观后感（见同目录 `观后感.txt`）
> 用途：记录我对咨询者四个问题的判断与做法，供后续答复、复盘时复用。

---

## 一、背景

对方在接入 AI Review 时遇到四个问题，并提到「初期还有点水花，后来慢慢流于形式」。

海哥我最近在项目中做 AI Review 也遇到一些问题，想请教一下：
1、怎么给 AI 足够的需求上下文：比如修改是否符合需求，我们要求提交代码都有一个单子，单子上会描述一些遇到的问题，但是很难保证非常详尽，且有时候还会带一些截图、文件、文档之类的附加信息，Review 的时候要把这些数据提供给 Review Agent 吗？目前感觉好像要实现这套自动下载日志、解析图片、读取需求文档的工作量很大，但是又不一定会有好的效果。因为修 Bug 、做需求的时候，更多的详细信息可能都在私聊，群聊中提到，只看单子中涉及到的内容可能是不及时的甚至是错的，这样反而影响了 AI 分析

2、怎么给 AI 足够的代码架构上下文：我想法是用 AST + LSP ，自己解析本轮代码改动后受到影响的代码模块，然后作为基础的上文提供给 LLM。但是感觉好像还不如直接丢一个完整的代码仓库目录，让 AI 自己 grep 、rg 来搜索分析。

3、怎么做持续的迭代优化：比如 Review Agent 给出的建议是否一定要用户给出反馈，否则不允许提交，强行作为 PR 必备环节？比如从 1 ~ 10 打分？然后定期的搜集所有的过去一段时间的 Review 的记录，看下低分的那一次的所有的请求链路是什么样的，为什么没有给出了低分的审核结果？
4、Skill 、MCP 还需要吗：我之前想法是每个模块要由模块负责人写一个 Skill，每次代码修改如果动到了这个模块，那么就调用到这份 Skill，按照模块负责人的思路解析。MCP 则是做一些提交记录搜索啊之类的功能。但是问题在于 Skill 如果要重度使用，那么 Skill 本身也要及时的更新迭代，但是人又经常容易遗漏这块。另外就是这个 Skill 应用了后，对于审核的结果到底是有用还是没用，是否还要做一个 Skill 的的应用情况的监测环节？

之前接入了一版 AI Review 效果，初期还有点水花，后来慢慢就流于形式了，发现想要做好还挺难的，比如准确度要怎么提升，AI Review 耗时要多久，Token 花费如何等等

1. 怎么给 AI 足够的需求上下文
2. 怎么给 AI 足够的代码架构上下文
3. 怎么做持续的迭代优化
4. Skill / MCP 还需要吗

我的总体判断：**他的四个问题，本质上是同一个问题——把 AI Review 当成了一个"合规环节"，而不是一个"判断系统"。** 一旦当成合规环节，就必然要求每 PR 必过、必须反馈、必须打分，最后退化成闭眼点通过。

## 二、逐条答复

### 1. 需求上下文：要爬，但要爬成结构

**我的做法**

- 用爬取把需求文档和 Figma 变成结构化 JSON：交互逻辑、原型关系、Figma 版本号，记录下载时间（快照版本）。
- 本地文档按章节分类，开发时对着快照记一次**实现基线**。
- 后续文档变动 → 用 Python 跑章节级 diff → 只同步差异点。
- 文档更新与实现是两条链路，互不阻塞。

**两个必须说清的前提**

- 快照只保证「和你拿到的一致」，不保证「是对的」。它把错误也一并固化了，只是加了时间戳。
- 评审必须绑**开发时的那一版**。否则需求改十版之后，用新需求去评旧代码，全是误报。

**为什么不做「把截图、文档、私聊内容直接喂给 AI」**

- 私聊、群聊里的信息没有结构，喂进去是噪声。
- 单子本身可能就是过时的，甚至写错的。
- 真正要解决的是「上下文的结构化与版本化」，而不是「上下文的完整性」。

### 2. 代码上下文：以 git diff 为准

**我的做法**

- 评审范围由 git diff 决定，改了什么就评什么。
- 我也没有更好的办法——全仓评审不可能，也没必要。
- LSP 这类工具只当**补充手段**：改到公共签名、DTO 字段这类契约面时，用它查直接引用，每个引用点只摘 3–5 行，判断「改完之后下游还成不成立」。
- 它不是让你审全仓，也不是替代 diff；它是「不用审全仓也不漏」的工具。

**它解决不了的**

- 跨仓 URL 契约（插件端 → 后端路由）：走字符串，不是符号。
- NestJS 装饰器 / DI 注册：不是标识符引用。
- Prisma schema ↔ 代码：类型对得上、表结构对不上。

**边界纪律**

- 引用点只作证据，不作评审范围；引用点自身的旧问题不进清单。
- 只做直接引用（1 跳），不递归。
- 脚本产出不计入「交叉验证 ≤3 次」的额度。

### 3. 持续迭代：反馈分三层，不能揉在一起

**第一层——报不报**

- 只把**必须看的重要问题**推给我。
- 其余汇进 TODO 清单，攒到下一轮、或下次做需求时统一处理。
- 小问题每次都来打断，才是真正影响效率的地方。

**第二层——严重度**

- P0–P3，按「触发条件 × 实际影响」定级。
- 问题严重度与「执行优先级 P0/P1/P2」是两套东西，不得混用。

**第三层——放行**

- 总判定只看有没有 P0/P1，是固定映射，不做主观发挥。

**迭代机制**

- 每轮评审写台账：判定、QN 清单、放行候选（含我驳回的条目与原句理由）、未覆盖项。
- 漏报归因四分法：没扫到 / 扫到但放行 / 报了没修净 / 已拍板。
- 隔一段时间按台账回灌，更新评审标准细节。
- 规则和 Skill 是逐句精挑的，不是自动生成的。

**明确不做**：强制用户反馈才能提交。这会把 AI 审核重新变成人工卡点，必然退化成点通过——正好是他说的「慢慢流于形式」。

### 4. Skill / MCP：Skill 本质就是模块职责规则

**我的做法**

- 每个目录有通用职责规则：这个目录放什么、依赖方向、分层边界。
- 复杂文件额外写一份链路说明：它应该长什么样、数据怎么流。
- 读或改这个文件时自动带出来，也能直接用于评审。
- 结构约束基本不迭代——它是项目结构与代码结构的设计问题，初期就该定好；真要改就是大手术，属于门禁留档的事。
- 会迭代的是「判断偏好」那一层，不是结构层。

**优于「每个模块负责人写 Skill」的地方**

- 规则挂在目录上，不挂在人身上，人走了规则还在。
- 不需要「Skill 有效性监测」——结构约束是机械可判定的，违反即报，不存在有效性存疑。
- 缺失即提示补写，靠流程保证，不靠人记得更新。

### 5. 为什么他最后会「流于形式」

- 把 AI Review 当合规卡点：必须每 PR 必过、必须反馈、必须打分。
- 正确姿势：只报重要的 + 小问题攒批 + 台账回灌归因。
- 耗时和 token 取决于标准写多严：条款严格、无发散空间，一次就能扫完；只有「分析有没有风险」这种模糊要求才需要多轮。

---

## 三、我明确不做的四件事

1. 不把截图、文档、私聊内容直接喂给 Review Agent。
2. 不做全仓评审，不把整仓库丢给模型当上下文。
3. 不做强制反馈卡点，不把「是否反馈」绑定到「能否提交」。
4. 不让模块负责人手写 Skill，不靠人自觉维护规则。

---

## 四、我承认的缺口

- 需求快照的可信度问题没有彻底解决：能保证「版本一致」，保证不了「内容正确」。
- 口头变更如果不回写需求文档，快照就会过期，而且看起来仍是最新的。
- AST / LSP 之外的三类契约（跨仓 URL、装饰器/DI、schema）目前没有自动化，只能人工对照。
- 没扫到的问题无法主动预防，只能事后归因、回灌规则。这是可接受的——但「知道了却不回灌」才是真问题。

---

## 五、一句话总结

**我不把 AI Review 做成卡点，而做成「优先级 + 批量降噪 + 台账归因」的判断系统；上下文靠结构化快照和 diff 划定范围，规则挂在目录上而不是人身上。**
